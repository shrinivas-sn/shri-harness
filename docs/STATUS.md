- Finding (23/09/2026, static, verified in source): the CI `hub=False` diagnostic cannot identify a hub on Windows. `sdk/packages/core/src/hub/daemon/index.ts` adds `--cline-hub-daemon` only when the embedded entry starts with `/$bunfs/`, but Windows compiled Bun uses `B:/~BUN/root/` (`apps/cli/script/build.ts:172`). Daemon mode is selected by the `CLINE_RUN_AS_HUB_DAEMON` env var (`apps/cli/src/index.ts:32`), not argv, so Windows hubs run without the marker. Every recorded `hub=False` survivor is therefore unclassified, not "not the hub". Recorded runs never captured survivor command line or PTY leader PID: the survivor's parent (844/924/8112/1428/8856) had always exited. The wrapper uses `spawnSync` (`apps/cli/bin/shri.cjs:135`), so the PTY leader exiting implies the TUI native child exited, unless Ctrl+C killed the wrapper first. Remaining hypotheses: (H1) TUI native child orphaned by wrapper Ctrl+C death, where parent == ptyPid; (H2) hub spawned by the TUI (prewarm or late spawn at shutdown), where parent is TUI shri.exe, cmd has `~BUN` entry and `--cwd`, and discovery is absent at cleanup time. Uncommitted diagnostic-only change records ptyPid/exitedAt/discovery presence and prints survivor redacted command line, creation time, parent state and locked leftover files. One hosted run decides H1 vs H2.
